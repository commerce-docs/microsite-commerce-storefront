You don't have to wait for Adobe to ship a feature you need, and you don't have to build a new drop-in to get it. The storefront is meant to be extended: a block is a small unit of UI you own, and drop-ins carry the tested commerce logic beneath it. When no existing drop-in container covers a feature, compose that drop-in's data and components directly inside your own block instead.

<Aside type="note">
This page assumes you already know how Edge Delivery Services loads a block, including the file conventions and `decorate()` function this pattern builds on, and that you've already tried wiring in a drop-in's pre-built container. The examples use the shared `CS_FETCH_GRAPHQL` instance and the `@dropins/tools` component provider, which your storefront includes by default. On an older or heavily forked project, confirm both are present before you start. For the standard way to add a drop-in to a block, see [Connect a drop-in](/dropins/all/quick-start/) first. Come back here only if no container fits your UI.
</Aside>

## Blocks and drop-ins

Before you build, it's worth clarifying what a block is and how it differs from a drop-in, because the two solve different problems:

- A **block** is a folder with a JavaScript file and a CSS file that decorates the semantic HTML Edge Delivery Services renders from an authored document. The table an author writes there is the contract — it maps directly to your block's markup, so you decide what an author can configure and what your code renders. You build, ship, and maintain it on your own timeline.
- A **drop-in** is a packaged commerce library Adobe builds and maintains, such as cart, checkout, and product discovery, with a stable API and its own release cycle. Integrating one into your blocks means you reuse tested, Adobe-maintained commerce logic instead of building and securing it yourself — you can customize and extend it, but you don't own or fork it.

The practical split: build a block for the storefront-specific feature you want, and rely on drop-ins for the tested commerce logic beneath it. The product comparison feature on this page is a **custom commerce block** — a block that composes a drop-in's data and components rather than shipping as a drop-in itself. It consumes the Product Discovery drop-in.

Composing is the lightest of three ways to extend the storefront — compose, extend, or create — and the one this page covers. Reach for extend or create only when composing can't do the job.

This pattern also costs less than creating a drop-in. Your code is plain JS and CSS that Edge Delivery Services decorates client-side, so there's:

- No new package to publish, version, or maintain.
- No drop-in SDK dependency to add.
- No separate build step.

The tradeoff: you maintain the composition logic yourself, and it won't appear in any drop-in's release notes or upgrade path. **Because you depend on functions the drop-in owns, watch that drop-in's release notes for changes to the signatures and payloads you call.**

## Before you write code

Before you build anything, answer one question: where does the data your feature needs live? The answer tells you which technique to use — and whether this page even covers it. The storefront talks to Adobe Commerce as a Cloud Service or Adobe Commerce Optimizer through GraphQL, so start by checking the GraphQL schema for the fields you need, then match your situation to the table.

<TableWrapper>

| Where the data lives | What to do | Where it's covered |
| --- | --- | --- |
| A drop-in container already renders the feature | Use the container as-is | [Connect a drop-in](/dropins/all/quick-start/) — you don't need this page |
| A drop-in's API returns the data, but no container renders the UI you want | Call the drop-in API function in your block | [Get data](#get-data), below |
| The field is in the schema, but no drop-in exposes it | Write your own GraphQL query | [Get data](#get-data), below |
| A drop-in's API is close, but its payload is missing a field | Extend the drop-in's data payload | [Extend](/dropins/all/extend-or-create/) |
| The field isn't in the schema at all | Extend the schema with App Builder | <Link href="https://developer.adobe.com/commerce/extensibility/" text="App Builder" /> |

</TableWrapper>

The rows that stay on this page both feed the [Get data](#get-data) tool below; the others hand off to another guide. You're never blocked: if the data isn't there yet, you can extend a drop-in's payload or the schema itself to expose it.

If the feature needs to persist new server-side state — its own mutations or a cart-like lifecycle — or needs a data model, containers, and events that no installed drop-in exposes, see [Extension options](/dropins/all/extend-or-create/) to compare that path against this one.

## Three tools to combine

Your storefront already has all three installed. A block combines them to build a new feature from existing drop-in artifacts: one **gets the data**, one **renders the UI**, and one **coordinates** with other blocks. The product comparison feature later on this page uses all three.

For the data, you choose how much to write yourself. Let a drop-in's API function fetch and shape the data for you, or write your own GraphQL query when no drop-in covers the field you need. You can mix these choices within one block.

The event bus sits outside that choice: coordinating blocks is a separate concern, not something a drop-in fetches or renders for you.

### Get data

You have two ways to fetch data, depending on coverage. Most of the time, let a drop-in's API function do it. When no drop-in exposes the field you need, drop down and write your own GraphQL query.

#### Call a drop-in API function

Find the drop-in that already handles the data your feature needs from the [drop-in list](/dropins/all/introduction/#available-drop-ins), then check its Functions reference page, such as [Product Discovery Functions](/dropins/product-discovery/functions/), for the function to call from its `api.js`:

```javascript
import { search } from '@dropins/storefront-product-discovery/api.js';

const { items } = await search({ phrase: 'hoodie', pageSize: 6 });
// items already have a predictable shape: price, images, and attributes normalized
```

It's the same function the drop-in's own containers use, so you write and maintain no query:

- The drop-in owns the GraphQL, its variables, and its versioning.
- A transformer runs on every raw response, so you get products in a stable, predictable shape instead of parsing raw GraphQL.
- Filtering and paging behavior stays consistent with the rest of the storefront.

#### Write your own GraphQL query

When the schema has the field you need but no drop-in exposes it, a block is just JavaScript, so nothing stops you from querying GraphQL directly. Use the shared `CS_FETCH_GRAPHQL` instance from `scripts/commerce.js` rather than the browser's `fetch`, so you don't re-implement the endpoint URL, store-context headers, authentication token, and cache-busting that every catalog request needs:

```javascript
// blocks/product-compare/product-compare.js
import { CS_FETCH_GRAPHQL } from '../../scripts/commerce.js';

const PRODUCT_COMPARE_QUERY = `query CompareProducts($phrase: String!, $filter: [SearchClauseInput!]) {
  productSearch(phrase: $phrase, filter: $filter) {
    items {
      productView {
        sku
        name
        urlKey
        images { url label }
        attributes { name label value }
        ... on SimpleProductView {
          price { final { amount { value currency } } }
        }
      }
    }
  }
}`;

// Store context, auth token, and customer group for pricing are already wired
const { data } = await CS_FETCH_GRAPHQL.fetchGraphQl(PRODUCT_COMPARE_QUERY, {
  variables: { phrase: '', filter: [{ attribute: 'sku', in: skus }] },
});
const products = data?.productSearch?.items?.map((item) => item.productView) ?? [];
```

The tradeoff is that you own the raw response shape: results come back nested under `items[].productView`, with prices split across `SimpleProductView` and `ComplexProductView`. Drop to this level only when a drop-in API doesn't cover your case.

</Option>

### Render UI

Render shared UI components, such as `Button`, `Image`, `Input`, and `PriceRange`, from `@dropins/tools/components.js` through a provider. These are the same components drop-in containers use, so instead of restyling pricing or re-optimizing images by hand, you render the real component into your own markup:

```javascript
import { PriceRange, Image, provider as UI } from '@dropins/tools/components.js';

await UI.render(PriceRange, { currency: 'USD', amount })(priceEl);
await UI.render(Image, { src, alt, params: { width: 400, height: 400 } })(imgEl);
```

Components inherit the storefront's design tokens, so your block matches the rest of the site without you copying styles. They also carry correctness you'd otherwise re-solve, with **accessibility baked in rather than bolted on later:**

- `PriceRange` handles currency and locale formatting, sale-versus-regular price display, and range calculations.
- `Image` produces Adobe Experience Manager Assets-optimized URLs and lazy loading.

See the [`.render()` reference](/sdk/reference/render/) for how the provider mounts a component into a DOM node, and the [component overview](/sdk/components/overview/) for the full set.

</Option>
<Option>

### Coordinate blocks

Emit and listen for events with `@dropins/tools/event-bus.js` so your block and other blocks on the page can coordinate without importing each other:

```javascript
import { events } from '@dropins/tools/event-bus.js';

events.emit('compare/products', { sku: 'MH01-XS-Black' });
```

Choose your own event name for a block-to-block signal that no drop-in emits yet. See [Events](/dropins/all/events/) for the shared naming conventions.

</Option>

## Walkthrough: Product comparison

The product comparison feature needs a table that shows up to three products side by side, plus a persistent tray that collects the products a shopper picks while browsing. No drop-in container covers that feature, but everything it needs already exists in your storefront. It uses all three tools without ever writing a raw query: the [`search`](/dropins/product-discovery/functions/) API gets the products, the SDK components format prices and images, and the event bus coordinates the two blocks. What's left is the logic specific to the feature: reading the selected SKUs, rendering the comparison table, and adding or removing products.

The steps below build this feature as two custom commerce blocks: `product-compare` for the table and `product-compare-bar` for the tray. The two blocks never reference each other. They coordinate through the event bus, a shared publish-and-subscribe channel where one block emits a named event and any others listening for it respond.

Each block is a folder with a JavaScript file, a CSS file, and an optional `README.md`, following the same convention as every other block on the storefront:

```plaintext
blocks/
  product-compare/
    product-compare.js
    product-compare.css
    README.md
  product-compare-bar/
    product-compare-bar.js
    product-compare-bar.css
    README.md
```

<Steps>

1. **Fetch data using a drop-in API function.** To look up the exact products a shopper picked, call `search()` with a `sku` filter:

   ```javascript
   // blocks/product-compare/product-compare.js
   import { search } from '@dropins/storefront-product-discovery/api.js';

   async function fetchProductsBySkus(skus, searchFilters = []) {
     const result = await search(
       { filter: [{ attribute: 'sku', in: skus }, ...searchFilters], pageSize: skus.length },
       { scope: 'product-compare-lookup' },
     );
     return result?.items ?? [];
   }
   ```

   The `searchFilters` argument carries the block's author-configured `filter` option into this same query, so the SKU lookup enforces the same eligibility rule as the rest of the block. **Without it, a shopper could request an ineligible product just by editing the `?compare=` URL directly.**

1. **Render the UI with SDK components.** For each product column, mount `Image` and `PriceRange`, plus a `Button` for the remove action — the same components a drop-in container uses, so the drop-in handles image optimization and price formatting:

   ```javascript
   // blocks/product-compare/product-compare.js
   import {
     Button, Icon, Image, PriceRange, provider as UI,
   } from '@dropins/tools/components.js';
   import { h } from '@dropins/tools/preact.js';

   await UI.render(Image, {
     src: image.url, alt: image.label || product.name, loading: 'lazy', params: { width: 400, height: 400 },
   })(imgWrap);
   await UI.render(PriceRange, { display: 'from to', minimumAmount, maximumAmount, currency })(priceWrap);
   await UI.render(Button, {
     icon: h(Icon, { source: 'Close' }),
     variant: 'tertiary',
     'aria-label': `Remove ${product.name}`,
     onClick: () => removeProductColumn(block, product.sku),
   })(removeWrap);
   ```

   Write your block's own CSS against the same [shared design tokens](/dropins/all/styling/#design-tokens-reference) the SDK components use, such as `--spacing-big` and `--spacing-medium`, so the table and tray don't look bolted on next to the rest of the page.

1. **Coordinate blocks with the event bus.** The Compare button is often added through a slot on an existing drop-in container, such as the `ProductActions` slot on the product-discovery `SearchResults` container, rather than in a custom commerce block. See [Extend](/dropins/all/extend-or-create/) for slot mechanics. Either way, the product list page doesn't know the comparison tray exists, and the tray doesn't know which block added a product. They only agree on an event name and a payload shape:

   ```javascript
   // blocks/product-list-page/product-list-page.js
   import SearchResults from '@dropins/storefront-product-discovery/containers/SearchResults.js';
   import { render as provider } from '@dropins/storefront-product-discovery/render.js';
   import { Button, Icon, provider as UI } from '@dropins/tools/components.js';
   import { events } from '@dropins/tools/event-bus.js';

   const getCompareButton = (product) => {
     const productName = product.name || product.sku;
     const wrap = document.createElement('div');
     wrap.className = 'product-discovery-product-actions__compare';
     // The entire integration: emit the event, let product-compare-bar react.
     UI.render(Button, {
       icon: Icon({ source: 'Bulk' }),
       'aria-label': `${labels.Global?.Compare ?? 'Compare'} ${productName}`,
       variant: 'tertiary',
       onClick: () => events.emit('compare/products', {
         sku: product.sku,
         img: product.images?.[0]?.url ?? '',
         name: productName,
       }),
     })(wrap);
     return wrap;
   };

   // Render the drop-in's SearchResults container and hook the button into its
   // ProductActions slot. Containers render through the drop-in's own `provider`;
   // shared components like Button render through the tools `UI` provider.
   provider.render(SearchResults, {
     slots: {
       ProductActions: (ctx) => {
         const actionsWrapper = document.createElement('div');
         actionsWrapper.appendChild(getAddToCartButton(ctx.product));
         actionsWrapper.appendChild(getCompareButton(ctx.product));
         ctx.replaceWith(actionsWrapper);
       },
     },
   })($productList);
   ```

   ```javascript
   // blocks/product-compare-bar/product-compare-bar.js
   import { events } from '@dropins/tools/event-bus.js';

   events.on('compare/products', ({ sku, img, name } = {}) => {
     if (!sku) return;
     const idx = products.findIndex((p) => p.sku === sku);
     if (idx !== -1) {
       products.splice(idx, 1);
     } else if (products.length < MAX_PRODUCTS) {
       products.push({ sku, img, name });
     }
     render();
   });
   ```

   Emitting `compare/products` again for a SKU already in the tray removes it, so the same Compare button can add or remove a product without tracking its own state.

   <Diagram caption="The product-compare-bar tray collecting products a shopper flags for comparison from a product list page">
     ![Apparel product list page with an Adobe pattern hoodie, a Pride at Adobe t-shirt, and an Adobe Life tee flagged for comparison, showing the persistent tray at the bottom of the page with Compare and Clear All buttons](@images/dropins/product-bar-page.png)
   </Diagram>

1. **Store state in the URL.** The comparison table's state — which SKUs to compare — doesn't need a drop-in or `localStorage`. Reading and writing that state to a URL query parameter means shoppers can share or bookmark the comparison page:

   ```javascript
   // blocks/product-compare/product-compare.js
   const skus = (new URLSearchParams(window.location.search).get('compare') ?? '')
     .split(',')
     .map((s) => s.trim())
     .filter(Boolean)
     .slice(0, MAX_PRODUCTS);

   // After adding or removing a product:
   const url = new URL(window.location.href);
   url.searchParams.set('compare', updatedSkus.join(','));
   window.history.replaceState({}, '', url);
   ```

   Reloading the page, sharing its URL, or bookmarking it now reproduces the same comparison, since every selection lives in the `?compare=` parameter.

</Steps>

## Best practices

- <strong class="keep-bold">Reuse the drop-in's options.</strong> Its existing filters, scopes, and pagination options work because you're calling the same function a container calls.
- <strong class="keep-bold">Name events `noun/verb`.</strong> Follow the convention drop-in events already use, such as `cart/updated` and `search/result`, so another developer can tell what your custom event does without reading its source.
- <strong class="keep-bold">Make events shareable.</strong> Design the event so any block with a matching trigger can emit it, not just the one you're building. A comparison tray listening for `compare/products` can respond to that same event from a product list page, search results, or a carousel, without a separate integration for each.
- <strong class="keep-bold">Reuse existing state.</strong> Before adding `localStorage` or a new global variable, check whether the URL or an event's last payload (`events.lastPayload()`) already has what you need.
- <strong class="keep-bold">Handle loading and errors.</strong> A drop-in container already renders a fallback when its data fetch fails, but your block calls the same API function directly, so it needs its own `catch` and an empty-results message.
- <strong class="keep-bold">Compose only when needed.</strong> Use this pattern only when no container covers the feature. If a drop-in container already handles most of the feature, extend it with slots or events instead of rebuilding its API function and components yourself.

## Hand your plan to AI

AI works best from a plan, not a blank prompt. The plan is the decisions this page walks through: whether to compose, extend, or create, and within a composed block, which parts reuse a drop-in API function, which reuse a drop-in component, and whether anything has to drop to a raw query.

Once that plan is clear, install [Boilerplate skills](/ai/boilerplate-skills/) so your AI coding agent can build from it. The skills encode this project's real conventions, so the agent looks up actual slot names, event payloads, and component props from the drop-in TypeScript definitions instead of inventing new conventions. A plan this concrete makes the generated code cheap enough to test, improve, or throw away.
