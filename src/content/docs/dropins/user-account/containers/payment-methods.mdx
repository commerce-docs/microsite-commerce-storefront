The `PaymentMethods` container shows saved payment methods for the signed-in customer (for example, cards saved at checkout). **Vaulting** means Adobe Commerce stores a **token** for the card (not the full card number) so the shopper can reuse that method later. You can show a full section or a **compact** row layout next to other account widgets. The list uses the same card styling as checkout flows through the `PaymentCard` component.

## Data loading

The container uses the `usePaymentMethods` hook in the `@dropins/storefront-account` package, which chooses a data source as follows:

1. **Event bus (eager)** — The hook subscribes to `account/customerPaymentTokens` on `events.on` with the listener option `eager` set to `true` so any existing payload is applied immediately. If an event payload is already available, the list is taken from the **event bus** and **no** GraphQL load runs on mount. Removing an item updates **local state only** (the `deletePaymentToken` mutation is not called).
2. **GraphQL** — If nothing is consumed from the bus, the hook calls **`getCustomerPaymentTokens`**. Removing an item calls **`deletePaymentToken`** with the token's **public_hash** value.

In the default **PaymentMethods** container, the shopper must **confirm in the removal modal** before the hook runs that delete (or the local-only update when the list came from the event bus).

Changing `filterPaymentMethodCodes` after the initial load triggers a refetch **only** when the current source is GraphQL (not when data came from the event bus).

<Aside type="tip" title="Injecting tokens from another drop-in">
Emit the **account/customerPaymentTokens** event with an array of display rows (the same shape as the **StoredPaymentMethodDisplay** model in the drop-in source) when you already have token data on the client—for example, after checkout or Payment Services initialization. Emit a **null** payload for an explicit empty list if your integration follows the same convention as the cart **cart/data** event.
</Aside>

## Remove confirmation

Removing a stored method is a **two-step** flow:

1. The shopper chooses **Remove** on a row. A **confirmation modal** opens (it can show a compact **PaymentCard** preview with brand, last digits, and expired state when that data is available).
2. **Cancel** closes the modal and does **not** call the API. **Remove** runs the **`deletePaymentToken`** mutation (or the equivalent path for your data source—see [Data loading](#data-loading)).

## Example

The following example shows the usual boilerplate pattern: initializer, container import, and `render` from the account drop-in.

```javascript
import '../../scripts/initializers/account.js';
import PaymentMethods from '@dropins/storefront-account/containers/PaymentMethods.js';
import { render as accountRenderer } from '@dropins/storefront-account/render.js';

export default async function decorate(block) {
  if (!checkIsAuthenticated()) {
    window.location.href = CUSTOMER_LOGIN_PATH;
    return;
  }

  await accountRenderer.render(PaymentMethods, {
    minifiedView: false,
    withHeader: true,
    // Optional: limit to specific gateway codes
    // filterPaymentMethodCodes: ['payment_services'],
  })(block);
}
```

For programmatic access to the same data and removal behavior outside this container, see [User Account functions](/dropins/user-account/functions/) for `getCustomerPaymentTokens` and `deletePaymentToken`, and [Events](/dropins/user-account/events/) for `account/customerPaymentTokens`.
