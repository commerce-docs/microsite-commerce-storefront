Developers often ask: “Should I build a new drop-in, or just add my functionality by extending the existing ones?” This guide provides a simple decision process, focusing on when NOT to extend a drop-in using the provided methods: slots, configuration, style overrides, and public events.

## Vocabulary

<Vocabulary>

### Extending a drop-in

Adding functionality to a drop-in using existing extensibility mechanisms like slots, configuration, styling, and events.

### Building a new drop-in

Creating a new drop-in from scratch using the [drop-in template](https://github.com/adobe-commerce/dropin-template) and SDK.

### Slots

Declarative anchors where custom UI content can be injected into a drop-in.

</Vocabulary>

## Do NOT build a drop-in for these scenarios

| Scenario | Why not? | Use instead |
|----------|------------------------------|-------------|
| **Third-party components** | They come with pre-built UI and JavaScript | Use the vendor's provided scripts (e.g., BV ratings) |
| **Simple content additions** | Overkill for basic content placement | HTML/CSS or slots |
| **Styling and UI changes** | Existing drop-ins can be customized extensively | Modify layouts, replace components, or use slots |
| **Merchant-specific logic** | Not reusable across different stores | Application-level conditional logic or configuration |
| **Experimental A/B variants** | Temporary and not yet proven for reuse | Feature flags or temporary code branches |

## FAQs

**Q: Are slots the *only* extensibility mechanism?**  
Slots are currently the primary stable extensibility mechanism. If they don't meet your needs, you can request new extensibility options through a formal feature request.

**Q: Can a third-party developer fully replace an out-of-the-box (OOTB) drop-in?**  
You *can* build your UI against the APIs directly rather than using drop-ins. However, you will have to re-implement all logic/functionality currently provided by an OOTB drop-in. We don't recommend this approach.
