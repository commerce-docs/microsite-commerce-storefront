This guide covers installation, Magento admin configuration, Fastly/production patterns, development guidance, and common debugging steps for using CORS with Adobe Commerce Storefronts.

<Aside type="caution">
**Use CORS only when necessary.** For production, prefer serving the storefront and the API from the same origin (for example, via Fastly VCL) to avoid CORS.

This guide combines information from the <Link href="https://github.com/graycoreio/magento2-cors" text="Graycore CORS module documentation" />, standard CORS specifications from <Link href="https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS" text="MDN Web Docs" />, and Adobe Commerce best practices.
</Aside>

## Installation and compatibility

Install the Graycore CORS module v2.x to your Adobe Commerce backend for Storefront API compatibility:

```bash
composer require graycore/magento2-cors:^2.0
php bin/magento module:enable Graycore_Cors
php bin/magento setup:upgrade
php bin/magento cache:flush
```

## Installation troubleshooting

### Version conflicts

If Composer reports conflicts, check your current version:

```bash
composer show graycore/magento2-cors
```

If you have v1.x installed, you need to upgrade:

```bash
composer require graycore/magento2-cors:^2.0 --update-with-dependencies
```

### Composer authentication errors

If you see "Could not find package", ensure your Composer authentication is configured for Adobe Commerce:

```bash
composer config --auth http-basic.repo.magento.com <public-key> <private-key>
```

Replace `<public-key>` and `<private-key>` with your Adobe Commerce access keys from your account.

### Module won't enable

If `module:enable` fails, check for:
- Typos in module name (it's `Graycore_Cors` not `Graycore_CORS`)
- File permissions issues
- Corrupted installation - try removing and reinstalling:

```bash
composer remove graycore/magento2-cors
composer require graycore/magento2-cors:^2.0
```

## Admin configuration

The Graycore CORS module adds a configuration section in the Adobe Commerce admin panel.

Navigate to **Stores → Configuration → Web → CORS Whitelist**:

### Allowed Origins

Add your storefront URLs, one per line (no trailing slashes):

```txt
http://localhost:3000
http://localhost:5173
https://staging-storefront.example.com
https://storefront.example.com
```

#### How origins are matched

- Must match exactly: protocol (`http` vs `https`), hostname, and port
- `http://localhost:3000` ≠ `https://localhost:3000` (different protocol)
- `http://localhost:3000` ≠ `http://localhost:5173` (different port)
- `http://localhost:3000` ≠ `http://127.0.0.1:3000` (different hostname)
- No trailing slashes: `http://localhost:3000` not `http://localhost:3000/`

<Aside type="caution" title="Development wildcard usage">
For development environments only, you can use `*` to allow all origins:

**Never use `*` in production.** Always specify exact origins. The wildcard exposes your Commerce APIs to any website - only use during local development.
</Aside>

### Allow Credentials

Enable this setting if your storefront needs to:
- Send authentication cookies
- Include session cookies
- Send credentials with cross-origin requests

When enabled, the `Access-Control-Allow-Credentials: true` header will be sent.

### Allowed Methods

Specify HTTP methods your storefront uses (comma-separated):

```txt
GET,POST,OPTIONS
```

#### Understanding preflight requests

Before sending the actual request, browsers send an OPTIONS request (called a "preflight") to check if the cross-origin request is allowed. This happens automatically for requests with:
- Custom headers (like `Authorization`)
- Methods other than GET/POST/HEAD
- Content-Type other than basic types

The OPTIONS request asks: "Can I send a POST request with these headers?"
The server responds with allowed methods, headers, and origins.

<Aside type="tip" title="OPTIONS method is critical">
Without it, all cross-origin requests will fail at the preflight stage.
</Aside>

### Allowed Headers

Specify headers your storefront sends (comma-separated):

```txt
Content-Type,Authorization,X-Requested-With,Store
```

Common headers include:
- `Content-Type`: For JSON requests
- `Authorization`: For bearer tokens
- `Store`: For multistore configurations
- `X-Requested-With`: For AJAX requests

## Common CORS errors

The following are standard CORS errors enforced by browser security policies. These error messages appear in the browser console (DevTools).

<Options label="Error" numbered={false}>

<Option>

### No 'Access-Control-Allow-Origin' header

```txt
Access to fetch at 'https://commerce.example.com/graphql' from origin 'http://localhost:3000' 
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the 
requested resource.
```

#### Cause

The CORS module is not installed, not enabled, or the origin is not in the allowed list.

#### Solution

- Verify the module is installed and enabled
- Add `http://localhost:3000` to Allowed Origins in admin
- Clear cache: `php bin/magento cache:flush`

</Option>

<Option>

### Origin not allowed

```txt
Access to fetch at 'https://commerce.example.com/graphql' from origin 'http://localhost:3000' 
has been blocked by CORS policy: The 'Access-Control-Allow-Origin' header has a value 
'https://storefront.example.com' that is not equal to the supplied origin.
```

#### Cause

The requesting origin is not in the allowed origins list.

#### Solution

Add the exact origin (including protocol and port) to the Allowed Origins configuration.

</Option>

<Option>

### Credentials flag issue

```txt
Access to fetch at 'https://commerce.example.com/graphql' from origin 'http://localhost:3000' 
has been blocked by CORS policy: The value of the 'Access-Control-Allow-Origin' header in the 
response must not be the wildcard '*' when the request's credentials mode is 'include'.
```

#### Cause

You have `Allow Credentials` enabled but are using `*` for allowed origins.

#### Solution

Replace `*` with specific origins when credentials are required.

</Option>

</Options>

### Common issues

If you encounter CORS errors after installing `adobe-commerce/storefront-compatibility`, verify that `magento2-cors` v2.x is installed. Earlier versions may not be compatible with Adobe Commerce Storefronts.

## Debug checklist

<Options label="Item" numbered={false}>

<Option>

### Verify module installation

Check the installed version:
```bash
composer show | grep graycore
```

Expected output: `graycore/magento2-cors 2.x.x`

Check module status:
```bash
php bin/magento module:status Graycore_Cors
```

Expected output: `Module is enabled`

</Option>

<Option>

### Verify admin configuration

Navigate to **Stores → Configuration → Web → CORS Whitelist** and confirm:
- Your storefront origin is in the Allowed Origins list
- Origins match exactly (including protocol and port)
- No trailing slashes in origins
- Allowed Methods includes `OPTIONS`
- Allowed Headers includes headers your storefront sends

</Option>

<Option>

### Inspect browser network traffic

Open DevTools → Network tab and look for:

#### Preflight OPTIONS request

```txt
Request URL: https://commerce.example.com/graphql
Request Method: OPTIONS
```

Expected response headers:
```txt
Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
```

#### Actual GraphQL POST request

```txt
Request URL: https://commerce.example.com/graphql
Request Method: POST
```

Expected response headers:
```txt
Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Credentials: true
```

</Option>

<Option>

### Check server logs

If CORS headers are present but requests still fail:

```bash
tail -f var/log/system.log
tail -f var/log/exception.log
```

Look for PHP errors, GraphQL exceptions, or module conflicts.

</Option>

<Option>

### Clear all caches

After any configuration changes:

```bash
php bin/magento cache:flush
php bin/magento cache:clean
```

Some CORS configurations may also be cached in Varnish/Fastly if applicable.

</Option>

</Options>

## Distinguishing CORS errors from server-side errors

When debugging, it's important to distinguish CORS policy failures from server-side GraphQL exceptions. Here's an example of a server-side error that might be mistaken for a CORS issue: 

```txt
{
  "message": "Internal server error",
  "extensions": {
    "debugMessage": "Magento\\InventoryConfiguration\\Model\\IsSourceItemManagementAllowedForProductType\\Interceptor::execute(): Argument #1 ($productType) must be of type string, null given"
  }
}
```

This indicates a PHP/GraphQL issue (inventory configuration or compatibility) and not a missing Access-Control-Allow-Origin header.

## Edge cases and special scenarios

### Docker and containerized environments

When running Commerce in Docker, you may need to add multiple origin variations:

```txt
http://localhost:3000
http://127.0.0.1:3000
http://host.docker.internal:3000
```

<Aside type="note" title="Docker hostname variations">
Docker networking can cause your browser to use different hostnames for the same service, so you need to add all variations.
</Aside>

### Multiple storefronts

For multiple storefronts accessing the same Commerce backend, add each origin separately:

```txt
https://storefront-us.example.com
https://storefront-eu.example.com
https://storefront-asia.example.com
```

Each storefront is treated as a separate origin and must be explicitly allowed.

## Adobe Commerce Cloud vs on-premise

### Adobe Commerce Cloud

- CORS configuration works the same way
- Ensure the module is installed in your environment
- Configuration syncs across Cloud environments through standard config management

### On-premise

- No differences in CORS setup
- You have full control over all infrastructure

## Production best practices

The recommended production approach is to avoid CORS by serving both the storefront and the backend from the same domain using a CDN proxy:

### Same-origin setup

- Storefront: `https://example.com` → CDN serves static assets
- GraphQL API: `https://example.com/graphql` → CDN proxies to Commerce backend

### Benefits

- Eliminates CORS preflight requests
- Reduces latency
- Simplifies security configuration

### Implementation with Fastly

Configure VCL to route `/graphql` requests to your Commerce backend while serving storefront assets from the CDN edge. This requires Fastly/VCL expertise and is typically handled by DevOps teams.
