<Aside type="caution" title="Production recommendation">
CORS should be a last resort for production. Prefer same-origin delivery of the storefront and API (for example, via Fastly VCL) to avoid CORS entirely.
</Aside>

## Quick test: Is CORS working?

If you already have CORS configured, test it by replacing `YOUR_STOREFRONT_URL` with your actual frontend URL:

```bash
curl -I -X OPTIONS https://your-commerce-backend.com/graphql \
  -H "Origin: YOUR_STOREFRONT_URL" \
  -H "Access-Control-Request-Method: POST"
```

Look for these headers in the response:
- `Access-Control-Allow-Origin: YOUR_STOREFRONT_URL` (or `*` if using a wildcard)
- `Access-Control-Allow-Methods: GET, POST, OPTIONS`

If you see these headers with your storefront URL, CORS is configured correctly. If not, follow the setup steps below.

## When do you need CORS?

Cross-Origin Resource Sharing (CORS) is a browser security feature that restricts web pages from making requests to a different domain than the one serving the page. CORS is required when your storefront runs on a different domain or port than your Adobe Commerce backend. For example:

- **Development**: Storefront at `http://localhost:3000` accessing Commerce at `https://commerce.example.com`
- **Staging**: Storefront at `https://staging-storefront.example.com` accessing Commerce at `https://commerce-staging.example.com`
- **Production**: Storefront at `https://storefront.example.com` accessing Commerce at `https://commerce.example.com`

Without CORS configured, browsers will block your storefront's GraphQL requests. You'll see an error in the browser console like:

```txt
Access to fetch at 'https://commerce.example.com/graphql' from origin 'http://localhost:3000' 
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present
```

This is a standard CORS error enforced by all modern browsers (Chrome, Firefox, Safari, Edge).

### Add CORS support

To add CORS headers to your Adobe Commerce GraphQL endpoints, you can configure your server, implement a custom module, or use a third-party CORS module (such as [graycore/magento2-cors](https://github.com/graycoreio/magento2-cors)).

If using a CORS module, install it via Composer:

```bash
composer require <module-package-name>
```

Refer to your chosen module's documentation for specific installation and configuration steps.

</Task>

<Task>

### Enable the module

If using a CORS module, enable it and run setup commands:

```bash
php bin/magento module:enable <Module_Name>
php bin/magento setup:upgrade
php bin/magento cache:flush
```

</Task>

<Task>

### Configure CORS in the Magento Admin

The module adds a **CORS Whitelist** configuration section in the admin panel.

Navigate to **Stores → Configuration → Web → CORS Whitelist** and configure the following fields:

<Aside type="note" title="Locating CORS settings in admin">
In the Commerce admin: **Stores** → **Configuration** → **Settings** → **Web** → **CORS Whitelist**
</Aside>

#### Allowed Origins

Specify which frontend URLs can access your Commerce backend. You need to set the actual URLs your storefront will use:

```txt
https://main--aem-boilerplate-commerce--hlxsites.aem.live
https://www.example.com
```

If you have multiple dynamic URLs (such as Edge Delivery Services branch previews like `main--repo--hlxsites.aem.live`, `some-branch--repo--hlxsites.aem.live`, and `localhost:3000`), you can use a wildcard:

```txt
*
```

<Aside type="tip" title="Why origins must match exactly">
Browsers check if the requesting origin (your storefront) is in this list. If not, the request is blocked. Each origin must match exactly, including protocol (`http` vs `https`) and port.
</Aside>

#### Allowed Methods

Set to: `GET,POST,OPTIONS`

<Aside type="tip" title="Why these methods are required">
`OPTIONS` is required for preflight requests. Use `GET` and `POST` for your GraphQL queries and mutations.
</Aside>

#### Allowed Headers

Set to: `Content-Type,Authorization,X-Requested-With`

<Aside type="tip" title="Understanding required headers">
These headers are sent with GraphQL requests. `Content-Type: application/json` is required for JSON payloads. `Authorization` carries authentication tokens. Add `Store` if using multistore.
</Aside>

#### Allow Credentials

Enable this if your storefront needs to send cookies or authentication credentials.

<Aside type="tip" title="When to enable credentials">
When enabled, browsers include cookies with cross-origin requests. This is required for session-based authentication.
</Aside>

</Task>

<Task>

### Test your CORS configuration

Open your storefront in a browser and check the Network tab in DevTools:
- Look for preflight `OPTIONS` requests to your GraphQL endpoint
- Verify the response includes headers like:
  - `Access-Control-Allow-Origin: <your-storefront-url>` (or `*` if using a wildcard)
  - `Access-Control-Allow-Methods: GET, POST, OPTIONS`
  - `Access-Control-Allow-Headers: Content-Type, Authorization`

If configured correctly, your GraphQL requests should succeed without CORS errors.

</Task>

</Tasks>

## Common pitfalls

<Aside type="caution" title="Avoid these common mistakes">

**Trailing slashes:** Origins should NOT have trailing slashes. Use `http://localhost:3000` not `http://localhost:3000/`

**Protocol mismatch:** `http://localhost:3000` and `https://localhost:3000` are different origins. Match exactly.

**localhost vs 127.0.0.1:** These are treated as different origins by browsers. If your storefront uses `http://127.0.0.1:3000`, add that exact URL.

**Forgot to clear cache:** After changing CORS settings, always run `php bin/magento cache:flush`. A stale cache is the #1 cause of "it's not working" reports.

**Using `*` with credentials:** You cannot use a wildcard `*` origin when `Allow Credentials` is enabled. Browsers will block the request.

**Missing `OPTIONS` method:** If you forget to include `OPTIONS` in Allowed Methods, all CORS requests will fail. All CORS requests start with an OPTIONS preflight request.

</Aside>

## Production best practices

<Options>

<Option>

### Same-origin architecture (recommended)

The best approach for production is to avoid CORS entirely by serving both your storefront and Commerce backend from the same domain using a CDN like Fastly:

- Storefront: `https://example.com` (static assets)
- Commerce GraphQL: `https://example.com/graphql` (proxied to backend)

This requires configuring your CDN to proxy `/graphql` requests to your Commerce backend.

**Benefits:**
- No CORS complexity
- Better performance (fewer preflight requests)
- Simpler security model
- Better caching control

**Implementation approaches:**

1. **Fastly VCL routing:**
   Configure Fastly to route GraphQL requests to your Commerce backend using VCL (Varnish Configuration Language). The VCL detects requests to `/graphql` and proxies them to your backend origin while serving other requests from your storefront origin.

2. **Cloudflare Workers / CDN Edge Functions:**
   Use edge functions to route API requests to your backend dynamically.

3. **Reverse proxy (Nginx/Apache):**
   Configure your web server to proxy `/graphql` requests to the backend.

**Resources:**
- <Link href="https://developer.fastly.com/reference/vcl/" text="Fastly VCL documentation" />
- Consult your DevOps team or CDN provider for implementation

**Note:** This approach requires CDN/infrastructure expertise. If you don't have these resources, use CORS configuration (Option 2) instead.

</Option>

<Option>

### CORS configuration

If you must use different domains (for example, `storefront.example.com` → `commerce.example.com`), use the CORS configuration above. Use specific allowed origins for single production domains, or a wildcard `*` when you have multiple dynamic preview URLs (such as Edge Delivery Services branch previews).

</Option>
