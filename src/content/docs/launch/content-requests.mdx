Content requests and page views do not have a one-to-one relationship. Learn which requests count, estimate content requests per page view, and use those estimates to plan for launch.

## Page views vs. content requests

When a shopper views a page, the browser makes many requests, but only some count toward your content request allowance. The main HTML page and its JSON data files count, but HTML fragments, Commerce API calls, and images, CSS, JavaScript, and other static assets don't. For example, the requests from one product page view add up to 2.4 content requests:

## Counted requests

Your storefront delivers pages through Edge Delivery Services, part of Adobe Experience Manager (AEM), so AEM's counting rules apply.

AEM counts successful responses, with status codes `100-299`, unless an [exclusion](#excluded-requests) applies. According to the <Link href="https://experienceleague.adobe.com/en/docs/experience-manager-cloud-service/content/implementing/using-cloud-manager/license-dashboard#what-is-a-content-request" text="AEM counting definition" />, these storefront requests count toward your allowance:

<TableWrapper>

| Request type | How it counts |
| ------------ | ------------- |
| HTML responses | Each HTML response, such as the page itself, counts as 1 content request. |
| JSON responses | Every 5 JSON responses, such as storefront data files, count as 1 content request. |
| Cached responses | Count the same as responses that aren't cached. |
| Prefetched pages | Count when loaded, even if the shopper never opens the page. |
| Automated traffic | Requests from scripts and monitoring tools count unless [excluded](#excluded-requests). |
| Visits that analytics doesn't record | Count, because AEM counts the content it delivers, even when a shopper's browser blocks analytics. |

</TableWrapper>

## Excluded requests

These storefront requests don't count toward your allowance:

<TableWrapper>

| Request type | What to look for |
| ------------ | ---------------- |
| Static assets | Images, style sheets, and JavaScript files. |
| HTML fragments | URLs ending in `.plain.html`, such as `nav.plain.html`. Fragments at other URLs, such as `/fragments/promo.html`, [count normally](#counted-requests). |
| Common Edge Delivery JSON files | `placeholders.json`, `placeholder.json`, `query-index.json`, and `form-data.json`. |
| Redirects and errors | Status codes `300` and above, such as `301` or `404`. The page that a redirect leads to [counts normally](#counted-requests). |
| Commerce API calls | Requests routed directly to Adobe Commerce without reaching AEM, such as `graphql` and `cs-graphql`. Calls to other services that don't reach AEM are also excluded. |

</TableWrapper>

AEM also excludes recognized search, social, and AI crawlers, DDoS attacks that it detects and blocks, and health checks that use `HEAD` requests. For the full list and ways to manage usage, see the <Link href="https://experienceleague.adobe.com/en/docs/experience-manager-cloud-service/content/implementing/using-cloud-manager/content-requests" text="AEM content request rules" />.

## Estimate content requests per page view

Use your browser's developer tools to estimate content requests for one page view on your storefront.

<Steps>

1. Open a page on your production site in your browser.

   Only production traffic counts toward your allowance.

    <Diagram caption="The examples on this page use this Adobe demo product page.">
       ![Demo storefront product page for the Pride at Adobe t-shirt, with product images, price, quantity selector, and Add to Cart button, followed by content cards, a team photo, product recommendations, and the footer.](./images/product-page.webp)
    </Diagram>

1. Open your browser's developer tools and then select the **Network** tab.

1. Select **Disable cache** and then reload the page.

   Disabling the cache shows the requests a first-time visitor makes. To include shopper actions in your estimate, interact with the page now, before you record your counts.

1. In the **Filter** box, enter the following filter. Replace `www.example.com` with your storefront's domain.

   ```text showLineNumbers=false
   domain:www.example.com mime-type:text/html
   ```

   At the bottom of the Network panel, record the number before the slash as your HTML count. This number shows how many requests match the filter.

   If no requests appear, check the domain in the filter and reload the page with the **Network** tab open.

    <Diagram caption="The HTML filter lists the page document and 4 fragments.">
       ![Chrome DevTools Network panel with Disable cache selected and the request list filtered to HTML responses from www.aemshop.net. Five responses with status 200 are listed: the page document and 4 .plain.html fragments.](./images/html-requests.png)
   </Diagram>

1. Replace the filter with the following one and record your JSON count the same way.

   ```text showLineNumbers=false
   domain:www.example.com mime-type:application/json
   ```

    <Diagram caption="The JSON filter lists 7 storefront data files and 6 Commerce API calls.">
     ![Chrome DevTools Network panel with the request list filtered to JSON responses from www.aemshop.net. Thirteen responses with status 200 are listed: 7 storefront data files, such as global.json and cart.json, and 6 graphql and cs-graphql requests.](./images/json-requests.png)
   </Diagram>

1. Subtract requests that match the [exclusions](#excluded-requests):

   - Redirects and errors: a **Status** value of `300` or higher, such as `301` or `404`.
   - HTML fragments: names ending in `.plain.html`, such as `nav.plain.html`.
   - Common Edge Delivery JSON files: `placeholders.json`, `placeholder.json`, `query-index.json`, or `form-data.json`.
   - Commerce API calls: requests routed directly to Adobe Commerce, such as `graphql` and `cs-graphql` in the example.

   If you're not sure how a Commerce request is routed, ask your storefront team before you exclude it.

1. Divide your remaining JSON count by 5.

1. Add that result to your remaining HTML count.

   The result is your content requests per page view.

</Steps>

### Example calculation

For the product page in the screenshots, these steps give about 2.4 content requests per view:

<TableWrapper highlightLast totalRow>

| Files | Browser requests | Content requests |
| ----- | ---------------- | ---------------: |
| Product page | 1 HTML | **1** |
| Fragments, such as the footer | 4 HTML | excluded = **0** |
| Storefront data files, such as `cart.json` | 7 JSON | 7 ÷ 5 = **1.4** |
| `graphql` and `cs-graphql` calls | 6 JSON | excluded = **0** |
| Total | 5 HTML, 13 JSON | **2.4** |

</TableWrapper>

## Forecast usage

Multiply each page's content requests per view by its expected views for your forecast period, then add the totals. For example, 10,000 views of the product page at 2.4 content requests per view use about 24,000 content requests.

The result is a starting forecast for shopper traffic. Before launch, review expected traffic and planned automated checks with your storefront team.

<Aside type="note" title="Estimated versus measured usage">

Your estimate reflects one test visit. Repeat visitors can make fewer requests, because their browsers cache some files.

For a site-wide comparison, ask your Adobe team or Adobe Customer Support to review measured usage, including eligible automated traffic. A top usage report shows what contributes most to your content request volume.

</Aside>
