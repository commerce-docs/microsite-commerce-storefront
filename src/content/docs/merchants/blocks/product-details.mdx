The `product-details` block renders the product detail page (PDP) for your storefront. Most shopper sessions go through a PDP before a purchase, so it is one of the most important Commerce blocks on your site.

If you are new to Commerce blocks, read [Authoring Commerce blocks](/merchants/quick-start/authoring-commerce-blocks/) first. It explains what you can change without code and what to hand to a developer. The rest of this page covers what is specific to the PDP.

## Where this block lives in your boilerplate

You do not add the `product-details` block from scratch. The Adobe Commerce boilerplate ships with PDP wiring already in place:

- A template page at `/products/default` uses the `product-details` block so you can preview and style a PDP in <Term>Document Authoring</Term> without a real product URL.
- Real shopper URLs follow the pattern `/products/<url-key>/<sku>` (for example, `/products/cool-hoodie/HOODIE-001`). The boilerplate reads the SKU from the URL and renders the same `product-details` block for every product.

Most of your edits happen on the template page at `/products/default`. The layout and styling you set there are inherited by every PDP. You add the block to a different page only when you are building a custom landing page that highlights a specific product. See [Feature a product on a marketing page](#feature-a-product-on-a-marketing-page).

<Aside type="tip" title="Confirm the template page exists">
Open `/products/default` in your content folder in Document Authoring. If the page is missing or empty, the PDP cannot render in preview. Copy the template from a fresh clone of the boilerplate content if you need to restore it.
</Aside>

<Callouts>

1. **Image gallery**: thumbnails or a carousel. See [`ProductGallery`](/dropins/product-details/containers/product-gallery/).
1. **Product header**: name and SKU. See [`ProductHeader`](/dropins/product-details/containers/product-header/).
1. **Price**: list price, plus a sale price when one applies. See [`ProductPrice`](/dropins/product-details/containers/product-price/).
1. **Short description**: a one- or two-line summary under the price. See [`ProductShortDescription`](/dropins/product-details/containers/product-short-description/).
1. **Options**: size, color, or bundle items for configurable and bundle products. See [`ProductOptions`](/dropins/product-details/containers/product-options/).
1. **Quantity selector**. See [`ProductQuantity`](/dropins/product-details/containers/product-quantity/).
1. **Action buttons**: Add to Cart and Add to Wishlist. The block renders these, not the underlying <Term>drop-in</Term>, so a developer can rearrange or restyle them in the block code.
1. **Full description**: the long product description. See [`ProductDescription`](/dropins/product-details/containers/product-description/).
1. **Additional attributes**: extra product attributes the catalog provides. See [`ProductAttributes`](/dropins/product-details/containers/product-attributes/).

</Callouts>

The `product-details` block is shared between B2C and B2B storefronts. For B2B-only experiences such as negotiable quotes, requisition lists, or purchase orders, use the matching B2B blocks listed in [B2B Commerce blocks](/merchants/blocks/b2b/).

### Property descriptions

#### default-sku

A product SKU the block uses when the page does not already supply one. The boilerplate reads `default-sku` only when the current page is the PDP template (the `/products/default` path) and the page is being edited in Universal Editor or previewed through Document Authoring. On any other page, or on the live storefront, the block uses the `sku` page metadata first and then falls back to the SKU at the end of the URL path.

In practice, set `default-sku` on `/products/default` so authors and reviewers can see a real product in preview. Setting it on other pages only has an effect on marketing pages that intentionally render the PDP outside the `/products/...` URL pattern.

### URL parameters the block reads

The `product-details` block also reacts to two URL search parameters. You do not set these in the block table. The boilerplate adds them when a shopper acts on the page:

- `itemUid` — switches the block into update mode for the cart line item with that ID. The add-to-cart button changes to an update button. This is set when a shopper clicks Edit on a cart line item.
- `optionsUIDs` — restores selected product options (for example, `size: large, color: blue`) when shoppers return from the wishlist or share a link.

Most authors do not need to think about these parameters. They explain why the PDP sometimes shows an Update button instead of Add to Cart.

## PDP-specific authoring tasks

These tasks are unique to the `product-details` block. For tasks that apply to every Commerce block — changing label text, restyling a section, adding companion blocks — see [Authoring Commerce blocks](/merchants/quick-start/authoring-commerce-blocks/).

### Preview a PDP on the template page

The block looks for a `default-sku` row when the page is being edited in Universal Editor or previewed in Document Authoring, so you can render real product data even though no SKU is in the URL.

<Steps>

1. In Document Authoring, open `/products/default`.

1. Add or update the `product-details` table with a `default-sku` row that points to a SKU in your catalog:

1. Save the page and open it in preview. The PDP renders using the SKU you set.

</Steps>

The `default-sku` value is only used on the template page and only in editor or preview mode. On a real product URL like `/products/cool-hoodie/HOODIE-001`, the SKU comes from the URL instead. You do not need to keep the template SKU up to date with real catalog changes.

<Aside type="caution">
Use this pattern sparingly. Every product in your catalog already has a working PDP at `/products/<url-key>/<sku>`. Adding a second hand-built PDP makes the campaign page harder to maintain when the catalog changes. Prefer linking from the campaign page to the canonical PDP whenever you can.
</Aside>

### Companion blocks for a PDP

A typical PDP includes more than just the `product-details` block. Add these companions to the same page, in this order, when you need them:

- A breadcrumb at the top of the page (boilerplate `breadcrumb` block).
- The `product-details` block.
- [Product Recommendations](/merchants/content-customizations/product-recommendations/) under the PDP to surface "You may also like" and similar carousels.

Each companion is a separate table in the same document. The `product-details` block does not need to know about the others; it just lives alongside them.

## Troubleshooting

In the browser developer tools console, two warnings point to common setup problems:

- `No defaultSku found in product-details block` — you opened `/products/default` in Universal Editor or Document Authoring preview but the `default-sku` row is missing from the `product-details` table. Add the row.
- `Unable to infer main image from JSON-LD or meta tags` — the page is missing the prerendered product metadata that the boilerplate uses to preload the hero image. Run the [metadata generation script](/setup/seo/metadata/#generate-metadata) for the catalog, or confirm the page metadata table includes a valid `sku`. The gallery still renders from the API; you only lose the preload.

If the Add to Cart button stays disabled, the product has required options (such as size or color) that the shopper has not selected yet. The block enables the button when the option selection becomes valid.
