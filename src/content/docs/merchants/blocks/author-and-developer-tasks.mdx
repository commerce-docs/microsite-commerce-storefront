Labels, block settings, spacing, scheduling, and which blocks appear on a page are all author tasks done in Document Authoring without code. New blocks and layout options belong to a page designer. Visual design and behavior inside a drop-in (colors, layout, how buttons work) belong to a developer. If your storefront uses templates for common content pages, start from the closest match instead of an empty page (see [How a page comes together](/merchants/quick-start/content-model/)).

## What you can change without code

Use tables and sheets in <Term>Document Authoring</Term>:

<TableWrapper>

| Task | Where to do it | Reference |
| --- | --- | --- |
| Choose which Commerce block appears on a page | The block table on the page | [Block table structure](/merchants/blocks/block-tables/) |
| Set the few settings a Commerce block accepts | The block table on the page | The Commerce block's reference page in [B2C Commerce blocks](/merchants/blocks/b2c/) or [B2B Commerce blocks](/merchants/blocks/b2b/) |
| Change the words shoppers see (button labels, headings, messages) | The placeholders sheet for the matching drop-in | [Labels and placeholders](/how-tos/change-labels-and-placeholders/) |
| Set the page title, description, and indexing | The metadata table on the page | [Page metadata](/merchants/blocks/page-metadata/) |
| Adjust spacing, background, and column widths around a Commerce block | A section-metadata table after the Commerce block | [Section metadata](/merchants/blocks/section-metadata/) |
| Translate labels into other locales | The locale-specific placeholders sheets | [Labels and placeholders](/how-tos/change-labels-and-placeholders/) |
| Add related blocks on the same page (for example, Product Recommendations) | Add another block table on the page | [Using Content and Commerce blocks](/merchants/blocks/content-commerce-blocks/) |
| Schedule when a page goes live | Snapshot scheduling in Document Authoring | [Scheduling options](/merchants/edge-delivery-services/scheduling/) |

</TableWrapper>

## What needs a page designer or developer

These changes require code or configuration outside the author tools. The **Who to ask** column names the role that usually handles each one:

<TableWrapper>

| Task | Who to ask | Why it is not an author task |
| --- | --- | --- |
| Add or remove an element inside a drop-in (for example, a wishlist button on the product page) | Developer | That element is part of the drop-in layout code, not your block table. A developer adds or removes it there. |
| Change the visual design of a drop-in (colors, fonts, button shapes beyond section metadata) | Developer | Visual design lives in your storefront's CSS and shared style settings. A developer edits those files. |
| Add a new block, or a new layout variation for an existing one (for example, an additional hero banner style) | Page designer | New blocks and layout variations — content blocks and Commerce blocks alike — are built in HTML, CSS, and JavaScript, then made available for an author to select in a block or section-metadata table. A page designer builds these, including wiring an existing drop-in into a new Commerce block. A developer is needed only when the change requires new drop-in code or a live catalog data feed beyond what an existing drop-in already provides. |
| Add a video to a page (outside product pages) | Page designer | The storefront code does not include a video block by default. A page designer adds one, such as the video block from the <Link href="https://www.aem.live/developer/block-collection" text="Block Collection" />. After that, you add a video with a block table and a link. Videos in a product's gallery come from the product in Commerce instead. |
| Track a new event in analytics or A/B testing | Developer | Drop-ins send events that other code can listen for. A developer connects those events to your analytics tool (for example, Google Analytics or Adobe Target). |
| Connect or change your storefront's connection to Adobe Commerce (endpoints, store view headers, services) | Integrator, often with a developer | These settings live in your [storefront configuration](/setup/configuration/commerce-configuration/). The integrator owns this work, often with a developer. |
| Add a drop-in that is not on your storefront yet | Developer | A developer installs the package and adds the Commerce block that loads it. |
| Change how a Commerce block behaves, not just how it looks (for example, how Add to Cart works) | Developer | The behavior comes from the drop-in code, not from the block table. A developer customizes the drop-in. |

</TableWrapper>

If the change is not in either table, file a ticket with the page URL, the block name (for example, `product-details`), and a description of your request.

## How a Commerce Storefront page is built

A page with shopping features combines three layers:

- <Term>Drop-in components</Term> — Adobe-shipped UI for Commerce features like Product Details, Cart, Checkout, and Account. A drop-in powers the interactive Commerce parts of a page (gallery, price, cart) and loads live catalog data from Adobe Commerce. Content blocks handle other page sections, such as marketing copy or images.
- <Term term="Commerce blocks">Commerce block</Term> — A <Term>Block table</Term> in your document with the block name (for example, `product-details` or `commerce-cart`) and any settings that block needs. See [Block table structure](/merchants/blocks/block-tables/) for the table shape.
- Page — The document that holds your Commerce blocks and any content blocks (marketing copy, images, and other content).

Most Commerce blocks live on a page you author yourself, such as your cart or sign-in page. The product page (PDP) is the exception. One document at `/products/default` is the template layout for every product URL, so a change there updates all product pages at once. Names, prices, images, and videos still come from your catalog, not from that document. See [Product Details](/merchants/blocks/product-details/) for how this template works.

#### Roles at a glance

- **Author** — Starts from a template and assembles a page in Document Authoring: adding text and images, and choosing which pre-built blocks appear. Also owns block settings, placeholders sheets, section and page metadata, publishing, and scheduling.
- **Page Designer** — Builds the blocks and layout options an author chooses from, including a block's styling, spacing, and behavior across devices. Requires HTML, CSS, Git, and JavaScript skills and works directly in the storefront's code, building new blocks and layout variations rather than drop-ins or their underlying behavior.
- **Integrator** — Connects the storefront to Adobe Commerce. Edits [storefront configuration](/setup/configuration/commerce-configuration/), store view headers, and similar settings, often with a developer when code is required.
- **Developer** — Owns code in your storefront repository: drop-in customization, new drop-ins, and analytics integrations.

On a small team, one person may perform two roles. Name the role you need on a ticket so the request reaches the right person faster.

For why this split exists, and how layout options get built before a content author can pick them, see [How a page comes together](/merchants/quick-start/content-model/).

For developer-facing vocabulary (containers, slots, events), see [Introduction to drop-in components](/dropins/all/introduction/).
