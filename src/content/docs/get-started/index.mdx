Adobe Commerce Storefronts are modern, headless shopping experiences built on **Edge Delivery Services** — fast by design, composable by architecture, and backed by the full power of **Adobe Commerce**. This documentation covers everything a developer needs to build, customize, and launch one, whether you're targeting B2C shoppers or B2B buyers.

## What is an Adobe Commerce storefront?

A storefront is the customer-facing layer of your Adobe Commerce site. Unlike a traditional monolithic storefront where the UI is generated server-side by Adobe Commerce itself, an Edge Delivery storefront is **headless** — the frontend is a separate, JavaScript-based application that calls Commerce APIs for its data and is delivered from CDN edge nodes worldwide.

This separation has a concrete consequence: pages load faster, Lighthouse scores are higher, and the frontend and backend can be developed, deployed, and scaled independently. Business users author content through [DA.live](https://da.live/); developers build commerce experiences using composable drop-in components; and Edge Delivery handles everything in between.

Adobe Commerce is your backend — catalog, pricing, inventory, orders, customers, and all the business logic that powers commerce. The storefront is the front door.

## Where storefronts fit in the Adobe Commerce ecosystem

Adobe Commerce comes in several deployment forms, and a storefront on Edge Delivery can connect to any of them:

**Adobe Commerce** is the core platform — a feature-complete, self-managed commerce engine available on cloud infrastructure or on-premises. It powers catalog, cart, checkout, order management, promotions, B2B features, and much more through its GraphQL and REST APIs. Version 2.4.7 or later is required for storefront compatibility.

**Adobe Commerce as a Cloud Service (ACCS)** is the fully managed SaaS deployment. Adobe provisions and operates the infrastructure, handles upgrades, and ensures availability. ACCS is the recommended deployment for new storefronts — it reduces operational overhead and provides automatic access to the latest Commerce capabilities and storefront services.

**Adobe Commerce Optimizer (ACO)** is Adobe's catalog and storefront performance layer. It sits between your Commerce backend and the storefront, providing ultra-fast catalog APIs optimized for high-traffic product browsing, search, and discovery — without requiring changes to your Commerce configuration. If your project uses ACO, your storefront calls its APIs for catalog data while still using Commerce for transactional operations.

**Edge Delivery Services (EDS)** is the delivery and rendering platform. Your storefront code lives in a GitHub repository; EDS pulls from it on every publish and serves pages from edge nodes close to your customers. This architecture is what makes Lighthouse scores of 100 achievable — there are no server round-trips on the critical path.

**Adobe Experience Platform (AEP)** and the Data Connection extension close the loop by streaming behavioral and transactional events from the storefront into Adobe's data platform. This powers personalization, product recommendations, Live Search, and analytics. It's not required to launch, but most production storefronts connect to it.

<Aside type="tip" title="Which backend do I have?">
If you're not sure which Commerce deployment your project uses, check with your Adobe account team or system integrator. The storefront setup steps are similar across all backends, but the API endpoints and service configuration differ. See [Prerequisites](/get-started/prerequisites/) for the checklist.
</Aside>

## The five building blocks

Every storefront is assembled from the same five pieces. Understanding what each one does — and doesn't do — before you start is the fastest path to confidence.

**Drop-ins** are the commerce UI components Adobe builds and publishes. Cart, Checkout, Product Details Page, Product List Page, User Account, Order History, Authentication — each is a self-contained npm package that renders a complete commerce experience, wires itself to Commerce APIs, and exposes structured extension points so you can customize it without modifying the source. Drop-ins are the most important concept in this documentation. Everything in the **Concepts: Drop-ins** section covers how to extend, style, and configure them.

**The Commerce boilerplate** is a GitHub repository template you use to scaffold your project. It wires together Edge Delivery, the SDK, drop-in registrations, CSS, and the block authoring system so you begin from a working storefront rather than a blank canvas. The boilerplate is a reference starter kit — your project is a snapshot of it at a point in time. When you see references to `scripts/commerce.js`, `styles/styles.css`, `blocks/`, or `config.json` throughout these docs, those are all files that live in your project, created from the boilerplate template. (Endpoints and headers live in **storefront configuration** — the JSON in `config.json` or the Edge Delivery config service — not in `commerce.js`.)

**The Storefront SDK** (`@dropins/storefront-sdk`) is the shared library that every drop-in is built on. It provides the initializer that sets up API connections, the UI component primitives that drop-ins use internally, design tokens that drive your visual theme, and utilities used across the stack. Most developers interact with the SDK indirectly — you call it directly when initializing drop-ins in `commerce.js`, using SDK components in custom UI, or creating a new drop-in from scratch.

**Commerce APIs** — primarily GraphQL, supplemented by REST — are how the storefront gets its data. Catalog queries, cart mutations, checkout flows, customer authentication, order retrieval: all of it goes through APIs hosted on your Commerce backend. API endpoints and authentication credentials are defined in **storefront configuration** (usually `config.json` at the repository root or values from the Edge Delivery config service). Each drop-in's initializer reads that configuration and calls the right endpoints.

**Edge Delivery Services** is the serving layer. It transforms documents (Google Docs or SharePoint tables) into HTML, decorates them with your block JavaScript, and delivers the result from the edge. No servers to manage. Your code is in GitHub; EDS deploys it. This is also where document-based content authoring lives — business users can manage non-commerce page content entirely without developer involvement.

[Core concepts](/get-started/core-concepts/) maps all five in detail, including how they connect at runtime. [Storefront architecture](/get-started/architecture/) has the full technical diagram and a layer-by-layer breakdown of the boilerplate's code structure.

5. **SDK** — [SDK introduction](/sdk/) for the CLI, [UI components](/sdk/components/overview/), and [API reference](/sdk/reference/).

6. **Guides** — Boilerplate setup and [storefront configuration](/setup/) when you're ready to connect Commerce APIs, configure CDN, and set up CORS.

7. **Performance** — [Performance best practices](/get-started/performance/) before you tune any loading behavior. Read alongside [Keeping it 100](https://www.aem.live/developer/keeping-it-100). Validate with [Lighthouse](/get-started/run-lighthouse/).
