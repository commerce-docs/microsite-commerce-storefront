## How the pieces fit together

Merchants author pages as documents. Edge Delivery Services turns those documents into HTML. Your Git repository runs JavaScript in the shopper's browser to load the right Commerce UI for each block on the page. Drop-in components inside those blocks call Adobe Commerce APIs to fetch real product, cart, and account data.

## Key concepts

### Edge Delivery Services

Edge Delivery Services (EDS) is Adobe's cloud delivery network for storefront pages. It turns authored documents into HTML and serves those pages from servers close to the shopper, so pages load fast. You do not manage servers or deployments. When you push code to GitHub, EDS builds and publishes automatically.

### Document Authoring and DA.live

Document Authoring is the way merchants create and update storefront pages without writing code. Pages are written as documents in Google Docs, SharePoint, or directly in <Link href="https://da.live" text="DA.live" /> (Document Author). Tables in those documents define the blocks on the page. Site Creator, the tool you use to provision a new storefront, also runs inside DA.live.

### Content blocks

A content block is a named section of a page that displays layout and marketing content — heroes, card rows, columns, headers, footers. Merchants author them as document tables. EDS converts each table into a `div` with a matching class name. Your repository holds the JavaScript and CSS that render that `div`. Content blocks do not call Adobe Commerce APIs.

### Commerce blocks

A Commerce block is a named section of a page that delivers interactive Commerce experiences such as cart, checkout, product detail, sign-in, and account. Merchants author Commerce blocks the same way as content blocks (a table in a document). The difference is what happens in the browser: the block's JavaScript loads a drop-in component and initializes it with your Commerce endpoint and configuration.

### Commerce boilerplate

The Commerce boilerplate is your Git repository. It starts from Adobe's <Link href="https://github.com/hlxsites/aem-boilerplate-commerce" text="Commerce boilerplate template" /> and holds everything your storefront needs to run: block decorators (one JavaScript file per block under `blocks/`), initializer scripts that configure each drop-in (`scripts/initializers/`), styles, and your storefront configuration file (`config.json`). This is the code you own, customize, and push to GitHub.

### Drop-in components

A drop-in component is an npm package (`@dropins/storefront-*`) that delivers a ready-made interactiveslice of Commerce UI. Examples include the site's cart, checkout, sign-in, product details, and so on. Drop-ins are loaded and initialized from a Commerce blocks. Then at runtime, drop-ins run entirely in the shopper's browser and call Adobe Commerce APIs directly. You install them with npm, configure them in `scripts/initializers/`, and extend or style them when the defaults are not enough.

### Adobe Commerce APIs

Adobe Commerce APIs are the GraphQL and REST endpoints that drop-in components use to read and write live Commerce data likeproduct details, cart contents, orders, account information, and so on. Adobe also provides hosted Commerce Services, including Catalog Service, Live Search, and Product Recommendations. These services are built to return catalog data to the storefront faster than the core GraphQL APIs.

<Aside type="note" title="Headless architecture">
This storefront is headless from Commerce's perspective. Edge Delivery Services serves the HTML and JavaScript. Drop-in components call Commerce APIs from the browser. You are not replacing the Commerce Admin, product catalog, or order management. You are only replacing the shopper-facing rendering layer.
</Aside>
