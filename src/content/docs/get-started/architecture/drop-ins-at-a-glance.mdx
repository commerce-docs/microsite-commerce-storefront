By the end of this page, you will know what a drop-in component is, why it talks to Adobe Commerce from the shopper's browser, and which docs to open when you are ready to install or customize one.

## What is a drop-in?

A drop-in component is a ready-made slice of storefront user interface (UI) and logic for one Commerce job, such as cart, checkout, or sign-in. Think of it as a packaged experience your page can show, instead of you writing all of that behavior from scratch.

Drop-ins are built for Adobe Commerce data. They call Commerce and related services through APIs using GraphQL to fetch and change data. You will see the full map of packages and screens in the [Drop-ins introduction](/dropins/all/introduction/).

## Where drop-ins run

Drop-ins run in the shopper's browser after the page loads. Edge Delivery Services (EDS) delivers the HTML, CSS, and JavaScript for the page. EDS does not sit in the middle of Commerce API calls for drop-ins. The drop-in component sends those requests directly to your configured endpoints.

<Aside type="tip" title="If data never loads in the cart or checkout">
If your Commerce environment is only reachable on a VPN or a strict IP allow list, remember that the shopper's device must be able to reach the same endpoints you configured. A setup that works for your laptop behind VPN may still fail for a shopper on a normal network.
</Aside>

## How you add drop-ins to a project

You install drop-ins the same way you install other JavaScript libraries, using npm (Node's package manager). Published package names look like `@dropins/storefront-cart`. The source code repos are private, but the built packages on npm are what your project depends on.

Your Commerce blocks and the files under `scripts/initializers/` load each drop-in and pass settings such as the GraphQL endpoint and translated labels. You do not paste drop-in UI into a document by hand the way you might for a simple content block. For the usual pattern, see [Using drop-ins](/dropins/all/quick-start/).

To see wiring in a real project, browse the <Link href={"https://github.com/hlxsites/aem-boilerplate-commerce"} text={"Commerce boilerplate repository"} />. When configuration is not enough, you can follow the [documented extension patterns](/dropins/all/extending/).

## B2C, B2B, and the package list

B2C means business-to-consumer (a typical shopper storefront). B2B means business-to-business (accounts, quotes, purchase orders, and similar flows).

The [Drop-ins introduction](/dropins/all/introduction/) lists B2C and shared packages. If you build B2B experiences, you will use extra packages and guides under [Drop-ins B2B](/dropins-b2b/) (company, quotes, purchase orders, requisition lists, and related topics).

These names show the pattern for consumer-facing drop-ins. Treat the per-drop-in install pages as the source of truth if a name or version changes. B2B installs are covered in [Drop-ins B2B](/dropins-b2b/).

- `@dropins/storefront-account`
- `@dropins/storefront-auth`
- `@dropins/storefront-cart`
- `@dropins/storefront-checkout`
- `@dropins/storefront-order`
- `@dropins/storefront-payment-services`
- `@dropins/storefront-pdp`
- `@dropins/storefront-recommendations`
- `@dropins/storefront-wishlist`
- `@dropins/storefront-personalization`
- `@dropins/storefront-product-discovery`
