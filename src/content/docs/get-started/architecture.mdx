Edge Delivery hosts your site. **Commerce blocks** use the boilerplate and **drop-ins** to reach your Commerce backend and services. **Content blocks** do not. This topic shows the big picture, then dives into the details.

<Steps>
1. Visual overview — How experience delivery and commerce share one Edge Delivery surface.
2. System stack — Content blocks vs Commerce blocks, drop-ins, boilerplate, backends, and shared services.
3. Runtime flow — What happens from a document table to a GraphQL response.
4. Reference — Boilerplate layers, drop-ins, Commerce services, then optional migration (Luma Bridge), event bus.
</Steps>

<Aside type="note" title="Content blocks compared to Commerce blocks">
In the [boilerplate terminology](/boilerplate/getting-started/#terminology), **content blocks** are the non-commerce Edge Delivery blocks (Cards, Columns, Headers, Footers, and more from the <Link href="https://www.aem.live/developer/block-collection" text="Block Collection" />). The [system stack](#system-stack) diagram labels them **Content blocks**—presentational layout and marketing UI. Edge Delivery renders them as HTML and optional decoration. They **do not** use Commerce-only `scripts/` wiring, load `@dropins/*` components, or call Adobe Commerce GraphQL. Only the **Commerce blocks** path continues from Edge Delivery into drop-ins and the boilerplate.

**Commerce blocks** use the same table-based authoring (for example, in DA.live) but are mapped in the boilerplate to initializers and `@dropins/*` packages. **Commerce** integration is the difference: Commerce blocks reach your Commerce backend **through drop-ins, `scripts/commerce.js`, and related configuration** (GraphQL and related APIs). Content blocks never do.
</Aside>

When the model makes sense, use [Commerce configuration](/setup/configuration/commerce-configuration/) to align your storefront with your Commerce backend (PaaS, Adobe Commerce as a Cloud Service, or Adobe Commerce Optimizer).

Each stage matches a box in the diagram. You create a table in the document (for example, Commerce Cart), or you use in-context editing. Edge Delivery Services turns it into HTML (for example, `<div class="commerce-cart">`). The browser loads that HTML. The block decorator runs in the browser, initializes the drop-in component, and the drop-in fetches from the Commerce API to render the UI.

The sections that follow document the same stack in more depth: [Boilerplate and blocks](#boilerplate-and-blocks) (files, decoration, and block wiring), [Drop-in components](#drop-in-components) (the UI packages), and [Commerce services](#commerce-services) (shared APIs and GraphQL behind the API node).

## Boilerplate and blocks

### Commerce boilerplate architecture

The <Link href="https://github.com/hlxsites/aem-boilerplate-commerce" text="Adobe Commerce boilerplate" /> uses a modular architecture that separates core AEM functionality from Commerce-specific features. That split keeps the codebase maintainable and aligned with the upstream AEM Boilerplate while preserving full Commerce capabilities.

In the repo, that split is AEM-style block delivery and decoration (shared with the upstream pattern) versus Commerce-only layers: `scripts/commerce.js`, `scripts/initializers/`, drop-in components, and API configuration that wire Commerce blocks to Adobe Commerce. The four layers below list the concrete files and folders.

### Four layers

These map to the [boilerplate `scripts/` folder](https://github.com/hlxsites/aem-boilerplate-commerce/tree/main/scripts) and `blocks/` in the [Adobe Commerce boilerplate](https://github.com/hlxsites/aem-boilerplate-commerce) repository.

<Steps>
1. `scripts/scripts.js` — Page load, block decoration, fonts, and imports from `scripts/aem.js` and `scripts/commerce.js`.
2. `scripts/commerce.js` — Commerce-specific loading, templates, and integration with the storefront configuration consumed from `config.json` (and related config).
3. `scripts/initializers/` — Bootstrap each Commerce drop-in component (account, cart, order, personalization, and so on), wire it to the storefront, and keep features integrated.
4. `blocks/`
   - Content blocks — Same authoring model as commerce (for example, DA.live tables). Edge Delivery renders server-side HTML (`<div>`s with block classes). Decorators can enrich markup, accessibility, and layout. They do not mount drop-in components or call Commerce GraphQL by themselves.
   - Commerce blocks — Mapped to initializers and drop-in components. They render interactive storefront UIs and load data through Adobe Commerce GraphQL and related APIs. For the repository layout, see [Getting started](/boilerplate/getting-started/).
</Steps>

## Drop-in components

Drop-in components are domain-driven Commerce UI packages (for example, `npm install @dropins/storefront-cart`). See the [Drop-ins introduction](/dropins/all/introduction/) for the full set. Commerce blocks and initializers mount them and call Commerce APIs. Customize them with [extension](/dropins/all/extending/) patterns.

<Aside type="note" title="Existing Luma storefront?">
Use [Luma Bridge](/setup/discovery/luma-bridge/) **only** when you are migrating or operating a **hybrid** experience: cart, checkout, or account still run on the **Luma** theme on Adobe Commerce PaaS while content and commerce marketing move to Edge Delivery. You do **not** need Luma Bridge for a greenfield Edge Delivery storefront, for Adobe Commerce as a Cloud Service + Optimizer with no Luma theme, or when the full funnel runs on drop-ins. Luma Bridge is a **session** layer on Commerce—it does not plug into or extend drop-in components; drop-ins run on EDS and set cookies that the bridge aligns with Luma.
</Aside>

You can add drop-ins to your project as npm packages:

- `@dropins/storefront-account`
- `@dropins/storefront-auth`
- `@dropins/storefront-cart`
- `@dropins/storefront-checkout`
- `@dropins/storefront-order`
- `@dropins/storefront-payment-services`
- `@dropins/storefront-pdp`
- `@dropins/storefront-recommendations`
- `@dropins/storefront-wishlist`
- `@dropins/storefront-personalization`
- `@dropins/storefront-product-discovery`

<Aside type="note" title="Extension patterns">
Adobe recommends using the [documented extension patterns](/dropins/all/extending/) for drop-in components.
</Aside>

## Commerce services

Commerce services are the shared APIs and capabilities your Commerce backend provides (for example, Catalog Service, Live Search, Product Recommendations, and core GraphQL), as shown in the [system stack](#system-stack) diagram. Drop-in components call them through the boilerplate and keep them on supported versions for the storefront to behave correctly.

For a complete list of merchandising services available for your Adobe Commerce storefront, refer to the <Link href="https://experienceleague.adobe.com/en/docs/commerce-merchant-services/user-guides/home" text="Adobe Commerce Services Guides" />.

Prerequisites and installation steps for each service vary by backend type (PaaS, Adobe Commerce as a Cloud Service, or Adobe Commerce Optimizer). See [Backend options](/get-started/backends/#prerequisites-by-backend) for the requirements that apply to your setup.

### Data Connection service

The Data Connection extension connects your Adobe Commerce storefront to the Adobe Experience Platform and the Edge Network so that you can enrich and personalize the experience for shoppers. See the <Link href="https://experienceleague.adobe.com/en/docs/commerce/data-connection/overview" text="Data Connection Guide" /> for details and installation instructions.

### Services Connector

The Services Connector connects your storefront to the Commerce backend services listed below. See the <Link href="https://experienceleague.adobe.com/en/docs/commerce-merchant-services/user-guides/integration-services/saas" text="Commerce Services Connector Guide" /> for details and installation instructions.

### Catalog Service

The Catalog Service module provides fast read-only access to Commerce catalog data. The Product Details drop-in component requires this service to render product data on the storefront. See the <Link href="https://experienceleague.adobe.com/en/docs/commerce/catalog-service/guide-overview" text="Catalog Service Guide" /> for details and installation instructions.

### Live Search

The Live Search service replaces the default Commerce catalog search. This service powers the Product Discovery drop-in, which provides customizable controls to showcase products and build interactive experiences for shoppers.

Live Search uses events to power search algorithms such as "Most Viewed" and "Viewed This, Viewed That". For headless requirements, see [Headless data collection](https://experienceleague.adobe.com/en/docs/commerce/live-search/workspace#data-collection) in the Live Search workspace. On Edge Delivery Services, implement required storefront events with [Storefront event collection](/setup/analytics/instrumentation/).

### Product Recommendations

Product Recommendations uses artificial intelligence and machine-learning algorithms (Adobe Sensei) to create personalized storefront experiences. Adobe recommends it for Commerce storefronts, though it is not strictly required. See [Product Recommendations setup](/merchants/blocks/product-recommendations/) for details.

Similar to Live Search, Product Recommendations uses events for collecting data to power recommendations. For headless storefronts, see [Headless integration](https://experienceleague.adobe.com/en/docs/commerce/product-recommendations/getting-started/headless). On Edge Delivery Services, implement required storefront events with [Storefront event collection](/setup/analytics/instrumentation/).

### Storefront Compatibility package

The Storefront Compatibility package extends the GraphQL schema provided with Adobe Commerce. It provides new mutations and adds missing fields needed by low-funnel drop-in components such as cart, checkout, user account, and order. PaaS customers must install this manually. Adobe Commerce as a Cloud Service and Adobe Commerce Optimizer manage it automatically. See [Storefront Compatibility package](/setup/configuration/storefront-compatibility/install/) for installation instructions and [PaaS: required packages and services](/get-started/backends/#paas-required-packages-and-services) for PaaS setup details.

See [Backend options](/get-started/backends/) for all prerequisites by backend type.

## Migration and hybrid patterns

The sections above describe the default path: commerce UI runs on Edge Delivery Services through the Adobe Commerce boilerplate and drop-in components. That is not always how teams migrate. Some projects move content and marketing to EDS first while cart, checkout, or account still use the Luma theme on Adobe Commerce PaaS. The topic below is only for that phased, dual-surface setup. If you are fully on drop-in components and EDS, you can skip to [Event system](#event-system).

### Luma Bridge (PaaS migration)

Use Luma Bridge on Adobe Commerce PaaS when Luma-themed cart, checkout, or account still run on Commerce while content and marketing move to Edge Delivery first.

Drop-in components vs bridge: [User authentication](/dropins/user-auth/) and [cart](/dropins/cart/) run only on EDS. They set cart and authentication cookies. Luma Bridge is a PHP module on Commerce that matches that cookie contract so Luma pages share session with EDS. It does not initialize or plug into drop-in components. Commerce adapts to what drop-in components already do.

For session details, see [How does session management work?](/setup/discovery/luma-bridge/#how-does-session-management-work). For topology and when not to use this approach (for example, PWA Studio or Vue Storefront), see the [Luma Bridge](/setup/discovery/luma-bridge/) guide.

<Aside type="note" title="Reading the diagrams">
EDS ↔ Luma Bridge means shared session cookies, not “the bridge hooks into drop-in components.” Drop-in components run on EDS. Luma Bridge on Commerce follows their cookies when shoppers move between EDS and Luma URLs.
</Aside>

For prerequisite details on PaaS + ACO Connector migrations, see [Backend options](/get-started/backends/#backend-topology).

## Event system

Drop-in components communicate through a shared event bus (`@dropins/tools/event-bus.js`) using publish-subscribe. Components stay loosely coupled. No drop-in component depends directly on another.

<Diagram type="mermaid" code={`
%%{init: {'theme':'base', 'themeVariables': { 'edgeLabelBackground':'#ffffff'}}}%%
graph LR
    Auth(User Auth)
    PDP(Product Details)
    Cart(Cart)
    Checkout(Checkout)
    Order(Order)
    Account(User Account)
    EB(Event Bus)
    YourCode(Your Code)

    Auth -->|"authenticated"| EB
    PDP -->|"pdp/data"| EB
    Cart -->|"cart/updated, cart/data"| EB
    Checkout -->|"checkout/updated"| EB
    Order -->|"order/placed, cart/reset"| EB
    YourCode -->|"locale, authenticated"| EB

    EB -.->|"authenticated"| Cart
    EB -.->|"authenticated"| Checkout
    EB -.->|"cart/updated, cart/data"| Checkout
    EB -.->|"cart/initialized"| Checkout
    EB -.->|"order/placed"| Cart
    EB -.->|"cart/updated"| Account

    linkStyle 0,1,2,3,4,5 stroke:#3b82f6,stroke-width:2px
    linkStyle 6,7,8,9,10,11 stroke:#6366f1,stroke-width:1.5px,stroke-dasharray:5

    style EB fill:#fef3c7,stroke:#f59e0b,stroke-width:3px
    style Auth fill:#f3e8ff,stroke:#a855f7,stroke-width:2px
    style PDP fill:#dbeafe,stroke:#3b82f6,stroke-width:2px
    style Cart fill:#dbeafe,stroke:#3b82f6,stroke-width:2px
    style Checkout fill:#e0e7ff,stroke:#6366f1,stroke-width:2px
    style Order fill:#e0e7ff,stroke:#6366f1,stroke-width:2px
    style Account fill:#f3e8ff,stroke:#a855f7,stroke-width:2px
    style YourCode fill:#fce7f3,stroke:#ec4899,stroke-width:2px
`} caption="Solid arrows: events emitted. Dashed arrows: events consumed. Your custom code (pink) can emit and listen to events alongside drop-ins." />

- **`events.on(name, handler)`** — subscribe; returns a subscription handle
- **`events.emit(name, payload)`** — publish an event
- **`subscription.off()`** — unsubscribe (call on the handle returned from `events.on`)

Each drop-in indicates which events it emits and listens to. See the [event bus API reference](/sdk/reference/events/) and the [drop-in events overview](/dropins/all/events/) for details.

<Aside type="tip" title="Events vs. analytics">
The event bus handles **internal** communication between drop-ins on the page. It is separate from [storefront events sent through the Adobe Client Data Layer](/setup/analytics/instrumentation/) for Adobe Commerce services (Live Search, Product Recommendations).
</Aside>
