Confirm that a new or changed storefront connection supports the content, catalog, and shopping features in your project's agreed scope. Start after the local or shared development preview is running.

This process is a development-readiness check, not a production launch review. Check only the features included in your project's agreed development scope.

## Before you start

Gather these details from the project owner or Commerce administrator:

- The local or shared development preview URL.
- The intended Commerce environment and store or catalog.
- A content page and an available product from that catalog.
- The product's expected price and currency for the shopper being tested.
- A search term and filter to test, if search is configured.
- An approved test account, if account features are required.

The storefront should already be running. For setup instructions, use [Create a storefront](/get-started/create-storefront/), [Run your storefront locally](/get-started/run-locally/), or [Storefront configuration](/setup/configuration/commerce-configuration/).

With Adobe Commerce Optimizer, identify both the catalog service and the platform that handles cart, checkout, and accounts. A successful catalog connection does not prove that the transactional integration is ready.

## Confirm the active configuration

Check the settings the storefront loaded, rather than only the settings saved in a file or configuration service.

Follow [Confirm the loaded configuration](/setup/configuration/commerce-configuration/#confirm-the-loaded-configuration) to compare the active endpoints and store or catalog context with the approved development settings.

Continue only when the values match. If they still point to a demo or another environment, resolve the configuration issue before testing shopping features.

## Check content and catalog data

Use known pages and products so you can distinguish a working connection from sample content.

<Steps>

1. Open the agreed content page in your development preview.

   Confirm that the expected heading, text, or images appear.

1. Open the agreed product page.

   Confirm that the product name and images match the intended catalog.

1. Compare the displayed price and currency with the expected values.

   Use the same store and shopper context that the Commerce administrator used to provide those values.

1. Search for the agreed term, if search is configured.

   Confirm that the results include the expected products.

1. Apply the agreed filter, if filtering is configured.

   Confirm that the displayed products match the selected filter.

</Steps>

If search or filtering is intentionally outside the current scope, record it as not applicable. If it is required but does not work, record a failed check rather than skipping it.

## Check cart and checkout

Run these checks when cart and checkout are part of the project. For a catalog-only development phase, record these features as outside the current scope.

<Aside type="caution" title="Use an approved test environment">
Use a test product and environment approved by your team. Do not submit an order or use real payment details during these checks. A separate end-to-end order test needs the team's approved test-payment procedure.
</Aside>

<Steps>

1. Select any required options on the test product.

   Skip this step if the product has no options.

1. Add the product to the cart.

   Confirm that the cart shows the selected product and options.

1. Change the quantity to another allowed value.

   Confirm that the cart updates the quantity and totals as expected.

1. Open checkout from the cart.

   Confirm that the expected cart items and checkout fields appear. Check any sign-in requirement against the project's intended behavior.

</Steps>

Opening checkout does not verify payment processing or order placement. Keep those results separate from this setup check.

## Check account features

Use these checks when customer accounts are included in the project.

<Steps>

1. Sign in with the approved test account.

   Confirm that the storefront shows the expected signed-in state.

1. Open the account page.

   Confirm that it shows the test account's information.

1. Sign out of the storefront.

   Confirm that the storefront returns to its expected signed-out state.

</Steps>

## Resolve failed checks

Start with the symptom that matches the failure. A working product page and a failing cart can indicate different backend connections, not a broken content page.

<TableWrapper>

| Symptom | What to check next |
| --- | --- |
| Content does not load. | Confirm the content source and preview URL using [Create a storefront](/get-started/create-storefront/) and the [local setup troubleshooting checks](/get-started/run-locally/#troubleshoot-local-setup). |
| Configuration still contains demo or old values. | Recheck the current origin, code branch, configuration source, and browser cache using [Storefront configuration](/setup/configuration/commerce-configuration/#confirm-the-loaded-configuration). |
| Products are missing or search returns unexpected data. | Confirm the intended store or catalog context. For Adobe Commerce Optimizer, check <Link href="https://experienceleague.adobe.com/en/docs/commerce/optimizer/setup/data-sync" text="Data Sync" />. If you use Adobe Commerce Optimizer Connector, also review <Link href="https://experienceleague.adobe.com/en/docs/commerce/aco-optimizer-connector/troubleshooting/troubleshooting-scenarios" text="Connector troubleshooting" />. For Catalog Service or Live Search configurations, use [Data export validation](/setup/discovery/data-export-validation/). |
| The browser reports blocked cross-origin requests. | Use [CORS Troubleshooting](/setup/configuration/cors-troubleshooting/) to investigate requests between the storefront and Commerce services. |
| Catalog data loads, but cart, checkout, or sign-in fails. | Check the transactional connection and [Backend options](/get-started/backends/). For Adobe Commerce, confirm the [Storefront Compatibility package](/setup/configuration/storefront-compatibility/). For a third-party platform, ask the integration owner to check its APIs. |

</TableWrapper>

When asking for help, include the page URL, intended environment, failed action, and error message. Remove account details, authentication tokens, and other sensitive data from screenshots or logs.

## Confirm readiness for development

Project setup is complete for the agreed scope when the required checks pass against the intended environment. Record the environment, tested features, failed checks, and any features explicitly outside that scope.

A required feature with an unfinished backend integration is still blocked. Do not treat a successful catalog check as approval for the whole shopping experience.

If you have not made a local code change yet, continue with [Make your first change](/get-started/first-change/). Otherwise, return to the planned feature work. Before production, complete the separate [Launch checklist](/setup/launch/launch-checklist/).
