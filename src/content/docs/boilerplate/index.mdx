Building a Commerce storefront from scratch means wiring up hosting, drop-in components, and Commerce APIs yourself. The Commerce boilerplate gives you that foundation already built, so you clone one repository and start customizing right away.

## What is the Commerce boilerplate?

The Commerce boilerplate is Adobe's supported starter/reference codebase for storefronts on <Term>Edge Delivery Services</Term> (EDS). You clone it from GitHub, connect your Commerce backend, and customize blocks, scripts, and styles in that repository instead of tying together every Commerce integration yourself. 

The boilerplate repository lives at <Link href="https://github.com/hlxsites/aem-boilerplate-commerce" text="hlxsites/aem-boilerplate-commerce" />. EDS hosts and publishes your site from that repo. The boilerplate also bundles <Term>Drop-in components</Term> for cart, checkout, product listings, and related Commerce flows so you theme and configure shipped UI rather than building those screens from scratch.

<Aside type="note" title="One supported boilerplate">
  <Link href="https://github.com/hlxsites/aem-boilerplate-commerce" text="aem-boilerplate-commerce" /> is the only Adobe-supported Commerce starter/reference storefront. Demo storefronts (for example Citisignal) are forks for events or showcases. They often lag behind this repository and are not a safe starting point for your own project.
</Aside>

## Exploring the code

The tree below shows the main folders plus important files at the repository root. The table links each folder to GitHub so you can open the matching source tree.

```text
aem-boilerplate-commerce/
├── blocks/                 # Commerce blocks and content blocks
├── scripts/
│   ├── aem.js               # core AEM/Edge Delivery runtime — do not edit
│   ├── scripts.js           # page load orchestration (eager, lazy, delayed)
│   ├── commerce.js          # Commerce loading, templates, storefront configuration
│   ├── delayed.js           # third-party scripts and analytics, loaded after initial render
│   ├── initializers/        # one initializer file per drop-in (endpoints, labels, and related settings)
│   └── __dropins__/         # generated drop-in assets from npm install — do not edit
├── styles/                 # global CSS, lazy-loaded CSS, and font-face declarations
├── fonts/                  # self-hosted font files
├── icons/                  # SVG icons used by blocks
├── models/                 # per-block Universal Editor definitions
├── tools/                  # the PDP metadata tool
├── cypress/                # end-to-end tests
├── build.mjs               # customizes the Commerce data drop-ins fetch (see Customizing blocks)
├── demo-config.json        # sample storefront configuration; copy to config.json for your project
└── package.json            # dependencies, scripts, and drop-in install hooks
```

## Running locally

If you still need to create the GitHub repository, connect Commerce, and initialize Document Author content, follow [Create a storefront](/get-started/create-storefront/) first.

Run the storefront locally so you can preview changes before you push them. If you already ran `git clone` while following [Create a storefront](/get-started/create-storefront/), start with the `npm install` step below.

<Steps>

1. Install the project dependencies.

   ```bash
   npm install
   ```

1. Start the local development server.

   ```bash
   npm start
   ```

1. Open `http://localhost:3000` in your browser.

</Steps>

Your storefront appears in the browser at `http://localhost:3000`.

<Aside type="tip">
If `npm install` fails, confirm that Node.js and npm are installed on your machine. If `npm start` fails, check whether another local server is already using port `3000`.
</Aside>

**Optional:** Install the `aem` command globally with `npm install -g @adobe/aem-cli` to run the CLI from any directory.

## Customizing your storefront

Styles, blocks, drop-ins, Commerce wiring, and third-party scripts each live in their own layer of the boilerplate. See [Customize blocks](/blocks/customize-blocks/) for which files and layers to change, which to leave alone, and when to isolate your changes in new files.

## Deploying your storefront

Edge Delivery Services creates preview and production URLs when you push changes:

- Preview: `https://<branch>--<repo>--<owner>.aem.page`
- Production: `https://<branch>--<repo>--<owner>.aem.live`

You do not run a separate deployment build command for Edge Delivery. The Edge Delivery pipeline handles page delivery and optimization after you push.

Push your production changes to the `main` branch. Caching and push invalidation only work as intended there, so other branches' `.live` URLs can serve stale content.

## Keeping your storefront current

Track boilerplate changes in the <Link href="https://github.com/hlxsites/aem-boilerplate-commerce/issues?q=label%3Achangelog+is%3Aclosed" text="Boilerplate changelog" /> and [Release notes](/releases/). For guidance on upgrading drop-in components, applying updates, and handling breaking changes, see the [Updates](/boilerplate/updates/) page.
