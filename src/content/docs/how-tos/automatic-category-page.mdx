When you need more category pages than you'd want to [author by hand](/how-tos/manual-category-page/), but the automated [AEM Commerce Prerender](/setup/configuration/aem-prerender/) solution doesn't fit your catalog's scale or requirements, you can generate the pages with a script. You produce the same category document — a `product-list-page` block plus a `metadata` block — but instead of authoring it in Document Authoring, you build it from a template, push it to Document Authoring through its Source API, and publish the path through the Edge Delivery Services pipeline.

This is a developer workflow: you write and run the script, and you own when it runs again.

<Aside type="note" title="How this differs from prerendering">
The [prerender solution](/setup/configuration/aem-prerender/) publishes category HTML as a [Bring Your Own Markup](https://www.aem.live/developer/byom) overlay and detects catalog changes for you. This approach instead creates a real, editable Document Authoring document, and there is no change detection — you re-run the script (or schedule it) to refresh a page. That trade is what lets you sidestep the prerender limits: you control the catalog query, the pagination, and the content that goes on each page. Treat this as an interim pattern until first-class support for large or custom category pages is available.
</Aside>

## How it works

<Steps>

1. **Fetch category data** from Commerce with your own catalog query (category metadata, and the products to list).
2. **Build a document** by injecting that data into a template that contains the `product-list-page` and `metadata` blocks.
3. **Create the document** in Document Authoring by posting it to the DA Source API.
4. **Publish the path** by calling the AEM Admin API to preview, then publish — the same preview/publish pipeline the rest of your site uses.

</Steps>

Re-run the script whenever the category or its metadata changes. The output is a normal Document Authoring document, so an author can still open and edit it afterward.

<Tasks>

<Task>

### Step 1: Fetch category data from Commerce

Query your Commerce backend for the category and the products you want to list. Use your own query — `YOUR_CATALOG_QUERY` below stands in for it.

```js
// Adobe Commerce as a Cloud Service / PaaS + Catalog Service: post to your Catalog Service GraphQL endpoint.
// Adobe Commerce Optimizer: post to your Merchandising GraphQL endpoint with your Optimizer headers.
const response = await fetch(CATALOG_ENDPOINT, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    // ...your store/context headers...
  },
  body: JSON.stringify({
    query: YOUR_CATALOG_QUERY,
    variables: { categoryPath },
  }),
});

const { data } = await response.json();
```

For ready-made category queries — fetching categories, the category tree, and product listing data by category path — see the queries in the <Link href="https://github.com/adobe-rnd/aem-commerce-prerender/blob/main/actions/queries.js" text="aem-commerce-prerender repository" /> (`actions/queries.js` on `main`), such as `CategoriesQuery`, `CategoryTreeQuery`, and `PlpProductSearchQuery`. For the schema each backend exposes, see the <Link href="https://developer.adobe.com/commerce/webapi/graphql/schema/catalog-service" text="Catalog Service GraphQL schema" /> (Adobe Commerce as a Cloud Service and PaaS) or the <Link href="https://developer.adobe.com/commerce/services/optimizer/" text="Merchandising Services guide" /> (Adobe Commerce Optimizer).

</Task>

<Task>

### Step 2: Build the document from a template

Render the category data into a Document Authoring document. A DA document is HTML with a specific shape: a `<body>` holding `<header>`, `<main>`, and `<footer>`, where `<main>` contains one or more sections (each a `<div>`). A block is a `<div>` whose class is the block name, with one `<div>` per row and one `<div>` per cell. This is the same markup Edge Delivery Services serves, so you can confirm the exact structure for any page by appending `.plain.html` to its URL.

Produce the same two blocks the [manual tutorial](/how-tos/manual-category-page/) describes — a `product-list-page` block bound to the category through `urlPath`, and a `metadata` block for SEO.

```html
<body>
  <header></header>
  <main>
    <div>
      <div class="product-list-page">
        <div>
          <div>urlPath</div>
          <div>apparel</div>
        </div>
      </div>
      <div class="metadata">
        <div>
          <div>template</div>
          <div>plp</div>
        </div>
        <div>
          <div>title</div>
          <div>Apparel</div>
        </div>
        <div>
          <div>description</div>
          <div>Shop the apparel collection.</div>
        </div>
        <div>
          <div>breadcrumb</div>
          <div>auto</div>
        </div>
        <div>
          <div>json-ld</div>
          <div>{ "@context": "https://schema.org", ... }</div>
        </div>
      </div>
    </div>
  </main>
  <footer></footer>
</body>
```

Fill the values from the data you fetched in Step 1 — the category's `urlPath`, title, description, and structured data. For the full list of metadata properties, see [Page metadata](/merchants/blocks/page-metadata/). Generate one document per category.

<Aside type="caution" title="Match the block markup exactly">
The block name must be the `<div>` class (`product-list-page`, `metadata`), and every row and cell must be its own nested `<div>` — not a `<table>`. Hand-assembling this markup per category is error-prone: prefer generating it, and confirm your output against a real page's `.plain.html` before you publish at scale. A malformed block is silently ignored, so the page publishes but renders no products.
</Aside>

</Task>

<Task>

### Step 3: Create the document in Document Authoring

Post the document to the <Link href="https://opensource.adobe.com/da-admin" text="Document Authoring Source API" />. The path you post to becomes the document's location in your content tree, which becomes the page URL — a document at `apparel.html` is served at `/apparel`.

```js
const form = new FormData();
form.append('data', new Blob([documentHtml], { type: 'text/html' }));

// path must include the file extension, e.g. apparel.html
await fetch(`https://admin.da.live/source/${org}/${repo}/${path}.html`, {
  method: 'POST',
  headers: { Authorization: `Bearer ${DA_TOKEN}` },
  body: form,
});
```

The Source API takes `multipart/form-data` with a `data` field holding the document, authenticated with a bearer token for your Document Authoring organization. A successful create returns `201`.

</Task>

<Task>

### Step 4: Publish the path through Edge Delivery Services

Creating the source document doesn't make it live. Publish it the same way the rest of your site publishes: call the <Link href="https://www.aem.live/docs/admin.html" text="AEM Admin API" /> to preview the path, then publish it.

```js
const base = `https://admin.hlx.page`;
const opts = { method: 'POST', headers: { Authorization: `Bearer ${AEM_TOKEN}` } };

// Preview, then publish. ref is your branch, typically "main".
await fetch(`${base}/preview/${org}/${site}/${ref}/${path}`, opts);
await fetch(`${base}/live/${org}/${site}/${ref}/${path}`, opts);
```

The preview call pulls your new document into the preview environment; the live call copies it to production and purges the CDN. After the live call succeeds, the category page is served at its path.

<Aside type="note" title="Authentication">
The AEM Admin API uses an admin token — the same credential the prerender app uses. See <Link href="https://www.aem.live/docs/admin.html#setting-up-authentication-for-admin-api" text="Setting up authentication for the Admin API" />. Treat both the Document Authoring and AEM Admin tokens like passwords: keep them out of source control.
</Aside>

</Task>

<Task>

### Step 5: Refresh when the catalog changes

Because there's no change detection, re-run the script to refresh a page after the category or its metadata changes. Run it on demand, or schedule it (for example, a cron job or a scheduled App Builder action) at whatever cadence your catalog needs. Re-posting to the same path overwrites the existing document, so re-runs are safe to repeat.

</Task>

</Tasks>

## Change a category page's URL

When you change the path your script generates for a category — for example, from `/apparel` to `/clothing` — publishing the new path is only half the job. The old path keeps serving the old document until you remove it, and once removed it returns a 404 unless you redirect it. This is the easiest thing to get wrong when you regenerate pages at new paths: the old URL gets orphaned, and you lose the inbound links and search equity pointing at it.

Whenever your generation logic changes a category's output path:

<Steps>

1. Generate and publish the document at the new path, following Steps 2–4.
2. Remove the old page: delete the old document from Document Authoring and unpublish its path through the AEM Admin API, so it's no longer served at the old URL.
3. Add a 301 redirect from the old path to the new one — for example, `/apparel` → `/clothing`.

</Steps>

You can automate the redirect in the same script: the `redirects` sheet is itself a Document Authoring resource, so append the old-to-new row and republish it. See [Redirects](/merchants/edge-delivery-services/redirects/) and <Link href="https://www.aem.live/docs/redirects" text="Redirects on AEM.live" /> for the sheet format, then update your [sitemap](/merchants/edge-delivery-services/sitemaps/).

<Aside type="caution" title="Never orphan the old URL">
Every path your script stops generating should either still resolve or 301-redirect to its replacement. If you change a category's URL key without adding a redirect for the old path, shoppers and crawlers that follow existing links hit a 404. Make the redirect part of the same run that publishes the new path, not a manual afterthought.
</Aside>

## Which approach should you use?

<TableWrapper nowrap={[0]}>

| Approach | Best for | Change handling |
|---|---|---|
| [Prerender](/setup/configuration/aem-prerender/) | Most catalogs; hands-off category and product pages | Automatic, on a fixed cadence |
| [Manually authored page](/how-tos/manual-category-page/) | One or a few categories, or a page that needs custom content | You edit the document |
| Generate programmatically (this tutorial) | Many category pages, or requirements the prerender limits block | You re-run the script |

</TableWrapper>
